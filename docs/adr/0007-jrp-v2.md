# ADR 0007: JRP v2 — binary-safe, bounded, streamable

Date: 2026-09-09. Status: accepted. Supersedes the v1 JSON framing for blobs.

## Context
v1 JRP represented blob payloads as UTF-8 strings inside JSON documents, fetched objects one at a time, and had no body limits or pagination. Binary files corrupt, large pushes allocate unbounded memory, and TypeScript interfaces were the only protocol contract.

## Decision
JRP v2 is JSON-over-HTTP with strict bounds and a binary escape hatch:
- Wire encoding of objects: structured objects (tree, state, provenance, evidence, contribution) as canonical JSON; blobs as base64 with an explicit byte length. The batch endpoints accept a maximum object size (default 4 MiB) and a maximum batch (default 32 MiB per request); the server rejects over-limit bodies with a typed error before reading them fully.
- Large blobs use dedicated binary endpoints: `PUT/GET /raw/:repo/:objectId` with Content-Length streaming (chunked transfer on the wire), so no 100 MB blob is ever materialized as a giant base64 document.
- All listings (log, layers, contributions, search) are paginated with opaque cursors and a server-enforced max page size.
- Version negotiation: clients send `x-jrp-version`; a server that does not support it responds with a typed `version_not_supported` error carrying its supported versions.
- The normative contract is `docs/jrp-spec.md` (wire format, endpoints, errors, limits, auth, CAS semantics, pagination, streaming, versioning). TypeScript types in `@javelin/protocol` are a projection of the spec, not the spec itself.

## Alternatives
- Fully binary framing (length-prefixed frames everywhere): fastest, but slower to debug and bind; JSON with bounds plus raw endpoints covers correctness now.
- gRPC/Protobuf: solves framing but adds codegen machinery and worse HTTP debuggability for one internal protocol.

## Consequences
- Backpressure on uploads is bounded by request limits and streaming raw endpoints; whole-repo-in-memory disappears.
- v1 consumers (sdk, javelind, cli, web) migrate in the same wave as the VCS core; no v1 compatibility is kept.
